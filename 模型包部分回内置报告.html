一、三轮变迁：内置集合是一条规则，不是启发式

版本内置什么iOS 产物为什么变
v0.2.6 ~ v0.2.8三份全内置约 1.8 GB装完即用，但换档位必须重出安装包
v0.2.9一份都不留48 MB安装包最小、档位自由，代价是首启要导三份
v0.2.10asr + opus826 MB本轮：常见的两条路开箱即用，最大的那份留给用户

「谁内置」不能是「取体积最小的那些」——推荐档位就是活证据：RECOMMENDED 里 translation 的推荐档是 Q4_K_M，而 models/ 里 Q3 更小。 任何隐式策略都会让它静默漂档，而输出看起来是「成功」。所以内置集合同样写死。

真源只有一处 —— scripts/model-tiers.py 顶部三张表：

RECOMMENDED   = {"asr": …, "translation": …, "opus": …}   # 建议用户装哪些
BUNDLED       = {"asr": …, "opus": …}                     # 随 App 分发哪些
NEVER_BUNDLED = ("translation",)                          # 刻意永不打进包里

约束 BUNDLED ⊆ RECOMMENDED 且 BUNDLED ∩ NEVER_BUNDLED = ∅，在 emit() 里用 die() 拦。同一个脚本新增两个模式：

  • --emit —— 唯一往 App 目录写东西的地方，先清空再重建两端产物（所以旧的 translation 不可能残留）；
  • --verify —— build-ios.sh 的那道闸。它不读 models/，只比对两端产物与表，因此干净克隆上也能跑（产物目录在 .gitignore 里）。
为什么必须有这道闸：最阴的坏法是「多内置一份」。一切正常工作，安装包凭空大 1 GiB， 没有任何报错。跨四层 —— 脚本表 / 两端源码 / 两端产物 / 工程文件 —— 而这几层里 只有工程文件那层会编译失败。

iOS 为什么必须是 folder reference

gen-ios-project.py 写的是 lastKnownFileType = folder;，不是 group。 group 会把目录压平到 bundle 根 —— asr/manifest.json 与 opus/manifest.json 撞名，后一个静默覆盖前一个，构建期完全看不出来。 验收判据（不能用 ls，要数 manifest）：

find X.app/BundledModels -name manifest.json   # 必须每个 kind 恰好一条

两端唯一的取包入口

static func selected(_ kind: Kind) -> URL? { installed(kind) ?? bundled(kind) }

任何一个调用点直接调 installed，内置那一份在那个点就永远看不到 —— 症状是「设置成智能选择但一直在用通用模型」，不报错，只是变慢。 Pipeline.loadOpusEngineIfPreferred() 就属于这种位置。

selected() 返回 nil 是正常状态，不是错误。translation 没有内置可回落， 首次启动它就是「未就绪」。两端都要按未就绪处理，并说清缺的是哪一份 （不是笼统一句「先准备模型包」）。另外 index.json 必须是顶层数组 —— iOS 的 bundledIndex 就是这么解它的，改成对象会让 App 静默读到空索引、三行全显「未就绪」。

四、负向验证：17 次注入，揪出三个假绿灯

项目约定是「没见它红过的判据不算判据」。所以 scripts/tests/test_bundled_models.py 的每条判据都喂了「故意写坏」的输入：注入 → 断言目标判据变红 → 逐字节还原 → 确认全绿。

假绿灯之一：判据按字面量数

BundledModels 这个字符串在 project.pbxproj 里出现 四次： 文件引用对象、构建文件对象、root group 的 children、Resources 阶段。 唯一决定「打不打包」的是最后那个。把它删掉，assertIn("BundledModels", text) 照样通过 —— 判据是假的。
同源坑：assertIn("--verify", text) 会被注释里的 --verify 骗过 （build-ios.sh:65 的注释里就有）。
两条都已收紧：前者改成语义判据（在 Resources 阶段那一段里数），后者只看非注释行。

假绿灯之二：快照式的「还原是否干净」是自指的

负向验证脚本第一版把还原核对写成「和开工时逐字节相同」——这是自指的： 开工时树里已经躺着一个脏文件，快照就把它记成基线，还原后「完全一致」✅， 这份垃圾被永久洗白，脚本报「干净」而判据其实是红的。
实测踩到了：assets/bundled-models/translation.vtmodel 因此一路留到下一次运行， 直到基线变红才暴露。
更糟的是它第一次还在 finally: undo() 里崩过：注入成功、还原锚点写错 → 崩溃 → 注入成了永久性的 —— 它悄悄删掉了 ModelPackages.swift 的 selected 回落， 而 git status 只显示「文件被改过」，和本轮正常改动混在一起看不出来。
两条硬规矩：① 快照之前先独立断言产物本来就对（不能复用被测判据，否则是用被测对象证明自己）； ② 还原靠开工时的字节快照，不靠反向 patch。

假绿灯之三：以为编了真机切片

build-ios.sh 默认只编模拟器。没加 --device 就去验收 Debug-iphoneos/，读到的是上一轮 14:40 的产物。 这类问题在 git status 里完全看不出来（ios/build*/ 在 .gitignore 里）。修法不是改脚本，而是固化验收动作：读产物版本号 + 看 mtime。

还有一类「失败」不是假绿灯，而是注入写错了

同一轮里有 4 条注入没有变红，但根因是注入的问题、不是判据的问题：

  • 锚点 '"opus": "opus-mt-zh-en-ja-v1",\n}' 在 RECOMMENDED 与 BUNDLED 里各出现一次，replace(…, 1) 命中了前者 —— 于是「往 BUNDLED 里加 translation」实际加进了 RECOMMENDED，判据当然不红；
  • 另一条注入的形状不对（写成 … = { 结尾，而计数判据只数以 , 结尾的行）；
  • 还有一条的还原锚点根本不存在。
这个区分本身很重要：分不清「判据是假的」和「注入写错了」， 就会去修一条本来正确的判据，或者把真正的假绿灯留在原地。
