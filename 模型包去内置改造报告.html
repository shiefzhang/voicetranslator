三、新接口：null 是正常状态，不是错误

两端现在都只剩「用户导入」这一条路。删掉内置之后最关键的一条契约是：

// iOS — ModelPackages.swift
static func installed(_ kind: Kind) -> URL?   // 取代 imported() ?? bundled()
static func isReady(_ kind: Kind) -> Bool     // installed(kind) != nil

// Android — ModelPackages.java
static File   selected(Context c, String kind)      // 唯一入口
static String displayName(Context c, String kind)
🔴 installed(_:) 返回 nil 不是错误 —— 首启按定义就没有任何包。 两端都必须把它渲染成「未就绪」并点名缺的是哪一份，不能只显示一句泛泛的「模型未就绪」。

首启点「开始」时的弹窗（两端同文案）：

还缺转写、翻译模型包。请在设置里点「导入模型包」选择文件，导入后即可完全离线使用。

判据：首启点「开始」→ 弹窗里必须出现具体缺哪一个（转写 / 翻译）； 只看到「模型未就绪」就是没做到这一步。设置页也加了分区标题 「以下三份模型包需自行导入（各一次即可，之后完全离线）」，徽章只剩 已导入 / 未就绪， 未就绪时按钮是「导入模型包」、就绪后是「更换」+「移除」。

四、真 bug：swiftc -parse 查不出名字遮蔽

本轮唯一一个真编译错误。把 imported(_:) 改名成 installed(_:) 之后：

ModelPackages.swift:349: error: cannot call value of non-function type 'URL'

成因：install(from:kind:progress:) 里写着

let installed = base.appendingPathComponent("\(manifest.id)-\(UUID().uuidString)")

这个局部量遮蔽了同名的静态方法 installed(_:) ⇒ installed(kind) 被解析成「对一个 URL 调用」。修法：局部量改名 activated，并留注释说明为什么不能叫 installed。

🔴 关键教训：swiftc -parse 对五个 Swift 文件全部报「语法 OK」 —— 它不做名字解析，所以局部变量遮蔽同名静态方法它看不见。 iOS 侧任何改名后的验收都必须是 bash scripts/build-ios.sh（真编译），不能只 -parse。

六、顺带修掉的假绿灯：安装失败却打印「✔ 已安装」

这是在做真机验证时撞上的：我用 CODE_SIGNING_ALLOWED=NO 编了个无签名真机包， 安装明确失败 ——

[ !! ] Error 0xe800801c: No code signature found. AMDeviceSecureInstallApplication(...)

—— 但脚本随后打印：

✔ com.shiefzhang.voicetranslator 已安装（Debug 构建）

根因

原代码把安装的退出码无条件吞掉，再由「设备上有没有这个 bundle id」下结论：

ios-deploy -i "$UDID" -b "$APP_PATH" || true          # ← 退出码丢了
...
if [ "$(ios-deploy -i "$UDID" -1 "$BUNDLE_ID" -e …)" = "true" ]; then
  echo "✔ … 已安装"
这个校验只能回答「设备上有没有这个 bundle id」，回答不了「装上去的是不是我刚编的这一份」。 所以「旧版本还装着 + 新包没装进去」会被打印成 ✔ 已安装（Debug 构建）， 而设备上跑的还是上一版 —— 正是本项目最忌讳的那类假绿灯。

修法：区分唯一的良性失败，其余一律降级

INSTALL_RC=0
ios-deploy -i "$UDID" -b "$APP_PATH" >"$INSTALL_LOG" 2>&1 || INSTALL_RC=$?

# 先确认 bundle 存在（这一步的语义没变）
# 再按退出码定性：
#   RC=0              → ✔ 已安装（并打出本地版本号）
#   日志含 0xe800002e → ✔ 已安装（已知良性：装完回查应用列表超时）
#   其它              → ✘ 安装没有成功（退出 1），并说明
#                       「设备上那个 bundle 只可能是更早安装的一版」

原来那条注释是对的（0xe800002e 确实良性），错的是把它当成了「所有失败的借口」。 现在良性路径按错误码精确匹配，其余非 0 一律失败退出。

九、体检器的三项判据（每项对应一个真实失败）

model-tiers.py 不再向任何 App 目录写东西，只做「列档位 + 体检能不能导入」。 三项体检各自的来历：

检查它挡住的真实失败判据
manifest.json 必须是 zip 的第一个条目 Android VtStoredZip 是顺序解析 local header 的，非首位直接拒绝： 「缺少有效 manifest.json，请选择 .vtmodel 模型包」 names[0] == "manifest.json"
含 licenses/ 许可登记要求逐包可追溯（OPUS 系列逐包许可不同） zip 里存在 licenses/ 前缀条目
有 ZIP64 记录 EOCD 里的中央目录偏移是有符号 32 位；越过 231 后读成负数 → invalid CEN header (bad signature) zip64_info(path)[0] >= 0
⚠️ manifest.json 优先这条是本次才第一次被检查的。 实测 models/ 下 7 个包全部以 manifest.json 开头， 但此前没有任何脚本或测试断言过它。model_pack.build() 是在循环之前 z.writestr('manifest.json', …)，所以不变量成立 —— 可一旦有人重排写入顺序，两端都会在导入时才炸。

推荐档位仍然是「钉死」的，不是「取最小」
