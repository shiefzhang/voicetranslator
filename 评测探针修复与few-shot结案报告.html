一、Bug #1：llama-completion -f 会吃掉 prompt 末尾恰好一个 \n

同一串、只改编尾的换行个数，读 prompt eval time = … ms / N tokens 里的 N：

prompt 结尾-p 传参-f 读文件说明
无换行4242一致
1 个 \n4342被吃掉 —— 这就是 bug
2 个 \n4343吃一个还剩一个（两个 \n 合成 1 token）
空格 + \n4443等价于只有空格
制表符4343没有末尾 \n 可吃
为什么这是生产路径问题：两端 App 是在内存里拼 prefix/suffix 的， suffix 末尾那个 \n 一定在 —— "<|im_end|>\n<|im_start|>assistant\n"（Qwen）、 "<end_of_turn>\n<start_of_turn>model\n"（Gemma）。 用 -f 就少喂一个 token，测的不是生产路径。

为什么藏了这么久：症状分引擎

  • ChatML 系（Qwen）几乎无症状 —— 对末尾换行不敏感，数字看着都正常。 所以过去所有 Qwen 的量化 / 指令集对照都「看起来没问题」。
  • Gemma 系症状明显但极易误判 —— 恒定吐一个垃圾前缀，然后给出正确译文： 
    disputa, トイレはどこですか？
onyms.明天早上八点三十分，火车去上海，但我还需要买票。
延续不好意思，请问您能告诉我如何到达车站吗？
টানা线地铁站距离最近？          ← 孟加拉文
ский                              ← 只剩西里尔字母
    第一句译对了，所以短样本一眼扫过去会通过；整体看起来就是「这个模型不行」。

修法与判据

改用 -p 传参（prompt 只有几百字节，远低于 argv 上限），并加 --no-escape —— -p 默认会把 \n 这类字面转义序列 当转义处理，而我们传的是真换行；实测加上它 token 数不变（43 → 43），纯属保险。

判据（可数、可复算）：prompt tok 比 -f 路径恰好多 1。 开整批前先跑一句核对 —— 本轮修完后 Gemma 单句的 prompt tok 从 81 → 82，译文同时变干净。

二、Bug #2：探针的 add_special=true 会多喂一个 BOS

谁调用结果
llama-completion（探针） common_tokenize(ctx, prompt, true, true) 会额外补一个 BOS
两端 App llama_tokenize(…, add_special=false, parse_special=true)
translator.cpp:37 / VTLlama.mm:57		 prompt 文本里的 <bos> 靠 parse_special 解析，恰好一个
tokenizer.ggml.add_bos_token探针 vs App后果
false（Qwen2.5 就是这样）等价 所以这个坑长期没露头
true（Gemma 系）探针喂 <bos><bos><start_of_turn>… 多一个 BOS，实测译文前面多出垃圾 token

修法不用改 prompt，运行时覆盖元数据即可：

--override-kv tokenizer.ggml.add_bos_token=bool:false
判据：覆盖后 <bos> 恰好 1 token、<bos>x 恰好 2 token （覆盖前是 2 / 3）。实测：<bos>→1、x→1、<bos>x→2，全部符合。

三、Bug #3（同源）：prompt 必须按 engine 分派

models/ 下同时躺着两个 kind=translation 的包， 而脚本默认会把它们都收进来。两个引擎的 prompt 毫无共同点， 连传进推理层的值都不一样：

engineprompt 形态few-shot传给引擎的是
llama-qwen2ChatML <|im_start|>…3 组英文语种名（Chinese）
llama-gemma3<bos><start_of_turn>user …无（单轮）语言代码（zh）

对应 Pipeline.java:206-207（boolean gemma=…; String from=gemma?source:languageName(source)） 与 PromptBuilder.swift:87，两端逐字一致。

拿 ChatML 去测 Gemma 的实测症状 —— 失控续写：第一句译对了，之后把 few-shot 当成「要接着补的内容」，开始编造不存在的例句，还把 <|im_end|> 当正文吐出来， 且不吐 EOG、硬吃到 256 token 上限： 
明天早上八点三十分，火车去上海，但我仍然需要买票。<|im_end|><|im_start|>userI have two cats.<|im_end|>
<|im_start|>assistant我养了两只猫。<|im_end|><|im_start|>userHow much does it cost to buy a new car?
…<|im_start|>assistant这本书的价格是20美元。<|im_start|>
「I have two cats. / 我养了两只猫。」从来不在任何 prompt 里，是模型续写出来的。 一眼看过去像「这个模型质量差」。

现在的做法：按包内 manifest 的 engine 分派，判不出来直接报错， 绝不默认按某一族处理。裸 gguf 没有 manifest，只能按 general.architecture 猜 —— 猜出来会把依据打出来。--shots 只对 llama-qwen2 有效， 对 Gemma 是空操作，脚本会明说且不下质量结论。

对齐 prompt 的权威来源与 BOS 必需性

唯一权威是 gguf 自带的 tokenizer.chat_template：把里面拼出来的字面量 逐字抄成代码模板（含每个 \n 的位置）。TranslateGemma 的模板里 {{ bos_token }} 就在最前面 ⇒ 手写模板必须以 <bos> 开头。

BOS 必需性的判据：把开头 <bos> 删掉再跑 —— 模型 直接空输出（立刻 EOG），说明它确实要求 BOS，那么「有且仅有一个」才是对的。

Qwen2.5-1.5B Q4_K_M，2 线程（= 生产值），greedy，仓库自带 20 条评测集， 探针已修（-p + BOS 覆盖）：

速度收益是真的

省下的正好是例句占的那部分：1 组能砍掉三成 prompt、三分之一冷 prefill。 「第一句特别慢」的来源就是换语向时要重新 prefill 这条 prompt，所以这个收益落在 用户真正感知得到的地方（非首句只 prefill 正文，不受影响）。

但质量结论不稳

chrF 随组数非单调：1 / 2 / 3 = 0.534 / 0.591 / 0.541。均值被少数用例主导 —— 3→2 时有 3 条 |ΔchrF| > 0.2，而且两侧都有：
用例3 组2 组Δ
en-zh-0030.1670.778+0.610
zh-ja-0050.1900.628+0.438
zh-ja-0030.8900.549−0.341
逐条分布：「变差 2 / 持平 13 / 变好 5」。20 条样本撑不起「换档位更好」的结论。
⚠️ 本轮最该记住的一条 —— 结论会随样本翻转：
样本逐条结果当时的判断
6 条临时用例6/6 不差、3 条更好看着无损，可以裁

翻转的方向完全由少数用例决定。样本量不够时，任何「无损 / 有损」的判断都不可信。

五、结论与重开条件

结论 1：few-shot 保持 3 组，不动生产值。 生产参数（translator.cpp ↔ PromptBuilder.swift）本轮零改动。
结论 2：内置翻译档位保持 Qwen2.5-1.5B Q4_K_M，不换成 Gemma 4B。 与 bundle-models.py 的 DEFAULT_PICKS 一致（实测 --list 仍选中 qwen25-1.5b-q4km-…-v1，内置合计 1843 MB）。

⚠️ 这份证据的效力边界（必须说清楚）

仓库自己的 evaluation/README.md 写着：内置数据集不能用于模型选型， 正式评测要求每方向至少 200 条。本轮的 20 条低于这条门槛。因此：

  • 本轮的 20 条证据只能用来 否决 一个改动（「裁 few-shot 的收益不足以抵消风险」）， 不能用来采纳 一个改动。
  • 本轮恰好只做了「否决」：不动。
  • 重开条件：按正式门槛准备每向 ≥200 条的配平数据，并把 |ΔchrF| > 0.2 的用例逐条人眼看一遍。

修正两个探针 bug 后，Gemma 的垃圾前缀完全消失（ Where is the nearest subway station? 拿到 chrF 1.000）， 说明那批垃圾确实来自探针、不是模型缺陷。但修完仍然：质量明显更差、速度慢 4.4× ⇒ 4 倍参数 + 更低比特 = 两样都输，「大模型质量更好」在这个档位组合上不成立。

尚未排除：Q3_K_M 对 4B 太狠。定性需要官方 F16 走 llama-quantize 做正规量化对照（本机包来自官方 google/translategemma-4b-it + 仓库自己的 prepare_translategemma.py，来历清白）。 张量表实测：Gemma 的 token_embd.weight 是 Q6_K、无独立 output.weight（tied embeddings）；Qwen 是 token_embd Q4_K + 独立 output.weight Q6_K —— 所以「lm_head 精度不足」解释不了，故本轮没有下这个结论。
