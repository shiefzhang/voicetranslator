DIAGNOSED · 2026-09-30 · v0.2.10 · 症状：中译日「每一句都慢」

专用引擎在 iOS 上
从来就没活过

问：「为啥这次的翻译那么慢，上次中日翻译还是很快的，是不是模型选错了？」

答：不是档位选错，也不是包选错。是 native/nmt/vt_ort.h 的一个编译期宏 VT_ORT_STATIC 从来没被定义过 —— 于是 OPUS-MT 专用引擎在 iOS 上一次都没装载成功， 每一句都静默回落到通用模型 Qwen（P50 1322 ms 对 OPUS 的 52 ms）。 这条链上每一步都「成功」：编译 ✅ 链接 ✅ 安装 ✅ 启动 ✅，界面上没有任何提示。

一页结论

0 处修复前 VTOpusNmt.o 对 ORT 入口的引用
修复后 1 处 U _OrtGetApiBase
56 处最终 binary 里的 Ort 符号
⚠️ 宏没定义时也是 56
2 道闸接进 build-ios.sh
构建前查配置 + 构建后查产物
10 / 10新判据的负向验证
逐字节还原后 109 项全绿
一句话说清根因：ios/Config/Base.xcconfig:53 用 $(VT_DEPS_DEFINES) 把编译期宏透传给编译器，而提供它的 scripts/setup-ios-deps.sh 从来没写过这一行。 Base.xcconfig:36-40 里连注释都写好了「依赖构建完成后会填 VT_ORT_STATIC」—— 设计在，实现没跟上。属于「半成品机制」，不是回归。

二、症状指纹：先把「慢」分成三种

「慢」这个词太粗，必须看形态。这也是排查时最先要问清的一件事：

形态指向本次
第一句特别慢，之后明显变快冷 prefill（3 组 few-shot 重喂 200~300 token）/ 冷读内置包，属正常代价排除
每一句都慢整条链路走的是通用模型（或通用模型档位导错）✓ 命中
卡很久，最后报「两次返回错误语种」译文复读顶到 256 token 上限 + 重试，指向 q4_0 那份包排除

用户补充的四条信息把范围收得很窄：方向 中→日（在 hybrid 表里，本该走 OPUS）、 引擎设 智能选择、同一台 iPad mini 4 上以前快、每一句都慢（非冷启动）。

三、排除法：四条假设都验过，都不是

假设怎么查的结论
内置集合错了ModelPackages.swift:195 是 installed ?? bundled、两端无 installed(.opus) 旁路；内置目录用 kind 而不是 id 拼路径✓ 正确，排除
ORT 没链进真机切片nm 真机 binary → 56 个 Ort* 符号⚠️ 这条证据是假的
装的是上一轮的旧产物源码 mtime 16:50:05 < 产物 16:54:18；.app 里 0.2.10/13 与本地 Info.plist 一致✓ 是这一轮编的，排除
导入的通用翻译包选错（q4_0 / Gemma 4B）陷阱真实存在（q4km 与 q4_0 只差几个字符，1.12 vs 1.07 GB），但症状应是「慢 + 偶尔译文发疯」不是本次原因
第三条假设差点把结论带偏。nm … | grep Ort 数到 56 个符号，看起来「ORT 接进来了」—— 但这只证明了归档被链上，证明不了宏被定义。见下一节。

四、根因链

ios/Config/Base.xcconfig:53
  GCC_PREPROCESSOR_DEFINITIONS = $(inherited) $(VT_DEPS_DEFINES)
                                          └── 由 Config/Deps.xcconfig 提供
                                              ↑ scripts/setup-ios-deps.sh 生成
                                              ↑ 那个脚本从来没写过这一行

→ VT_DEPS_DEFINES 恒为空
→ native/nmt/vt_ort.h:44-46 落到 return nullptr
→ vt::Api() == nullptr
→ VTOpusNmt.isAvailable() == NO
→ OpusTranslationEngine.init 抛 nativeUnavailable("ONNX Runtime")
→ Pipeline.loadOpusEngineIfPreferred() 静默 return nil
→ 每一句都走 Qwen（P50 1322 ms 对 OPUS 52 ms）

那个三分支长这样

inline const OrtApiBase *OrtApiBaseHandle() {
#if defined(VT_ORT_DYNAMIC)      // Android：dlopen("libonnxruntime.so")
  ...
#elif defined(VT_ORT_STATIC)     // iOS：静态链，直接调 OrtGetApiBase()
  return OrtGetApiBase();
#else
  return nullptr;                // ← iOS 一直走的是这里
#endif
}

VT_ORT_DYNAMIC 只给 Android 定义（app/src/main/cpp/CMakeLists.txt:43）。 全仓库 grep 下来，iOS 侧两个宏都没有。

五、🔴 为什么一直没被发现：「符号在」≠「宏在」

libonnxruntime.a 是被 VT_DEPS_LDFLAGS 整体链进 App 的 （sherpa-onnx 本来就用它）。所以在最终 binary 里数 Ort 符号完全是假绿灯：

nm VoiceTranslator.app/VoiceTranslator | grep -c Ort
宏定义了   → 56
宏没定义   → 56      ← 假绿灯就在这一行

唯一能区分的判据是编译单元：宏生效时 VTOpusNmt.o 里必然产生一个 未定义引用 U _OrtGetApiBase；宏不生效时那个引用根本不会产生。

nm …/Objects-normal/arm64/VTOpusNmt.o | grep OrtGetApiBase
修复前：0 处（真机 + 模拟器两个切片都是）
修复后：1 处   U _OrtGetApiBase
⚠️ 改 xcconfig 不保证触发重编。判据跑在陈旧的 .o 上会给出假绿灯 —— 必须 --clean 或 touch 源文件。verify-opus-linkage.py 的错误信息里写明了这一条。

六、修法：两处改动，缺一不可

文件改动为什么
scripts/setup-ios-deps.sh write_deps_xcconfig() 在各平台都有 libonnxruntime.a 时写 VT_DEPS_DEFINES = VT_ORT_STATIC 不修这里，下次重跑依赖构建就把宏冲掉了 —— 问题会无声复发
ios/Config/Deps.xcconfig 现网这份补上同一行 或 bash scripts/setup-ios-deps.sh --config-only 重写（两者逐字节一致）
新增 --config-only 的理由是防错，不是省时间：没有它，下一个人补这个宏时会去手工改 Deps.xcconfig —— 而那个文件第一行写着「请勿手工维护」，下一次 setup 就冲掉了。

为什么只在「各平台都有」时才定义：只在其中一个平台有 ORT 的话，另一个平台会变成 「宏定义了但库不在」→ 链接期 Undefined symbols: _OrtGetApiBase， 等于把静默故障换成编译失败，也是退步。

七、两道闸 + 一条真判据

闸 1（构建前，快）：配置里有没有那个宏

python3 scripts/verify-opus-linkage.py --check-config

闸 2（构建后，真判据）：目标文件里有没有真的生效

python3 scripts/verify-opus-linkage.py --build-dir ios/build

两道都接在 build-ios.sh 里，产物那道顶格写 —— 不挂在 if [ "$GATE_VARIANTS" = "1" ] 下面，免得被 --no-variant-gate 顺手关掉。

守它的测试：scripts/tests/test_opus_linkage.py（10 条）

其中三条是对自己的反向验证 —— 用真编译出来的两个 .o 对撞：

  • 只引用普通符号（对应宏没生效） → 判据必须 exit 1
  • 引用 OrtGetApiBase（对应宏生效） → 判据必须 exit 0
  • 一批里混一个坏的 → 整体必须变红（多切片构建会同时产出两份）

这三条如果哪一天变成「两边都通过」，说明判据退化了。

十、⚠️ 仍未验证的事（别当成已完成）

A8 上的绝对延迟仍然未知。修复只保证专用引擎「够得着」， 不保证它在 iPad mini 4 上「更快」。 仓库里那份 NMT换引擎门禁报告.html 第 9 节自己写着边界：
「但没有任何一条能证明它在 A8 上依然赢……这个 25× 是桌面读数，不是 iPad mini 4 的读数。 ORT 的 macOS wheel 降不到 armv8-a 基线，而 llama.cpp 侧能。 也就是说：OPUS 的真实优势有多少来自 dotprod，我们完全不知道。 ……两侧都未在 iOS/Android 真机上测过。」

要闭合这个缺口，只有一件事可做：在 iPad mini 4 上用同一套语料，把 llama.cpp 与 ORT 各跑一遍。 在那之前，「中译日该不该走 OPUS」这条策略都只是桌面数据支撑的假设。

另外，端侧 OPUS 的端到端（装载 548 MiB 包 → 中译日真的出译文）在真机上同样未实测 —— 这次修好的只是「装得起来」这一步。
