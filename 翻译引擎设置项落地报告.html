「中译日算进来、日译中不算」不是随手挑的。 依据 2026-09-28 的 20 条 / 4 语向门禁：zh→ja OPUS 赢（关键错误率 33% vs 50%）； zh↔en 打平；ja→zh 是最弱的一向（75% vs 50%）—— 官方根本没有 ja→zh 模型，只能 ja→en→en-zh 两跳，误差会叠加。 端侧包因此只装三条接线，刻意不含 ja-zh。

二、两端接线：三层判定 + 静默回落

设置项只表达意图；真正决定用哪个引擎的是 Pipeline 装载时的三层判定。 每一层都能独立地让这次会话回到通用模型 —— 所以这个选项永远不会把 App 变砖： 「智能选择」在没有 opus 包的构建上等价于「统一模型」。

三、模型包契约扩到三档 kind

原来的 asr / translation 之外新增 opus。 它有一处结构性不同：OPUS 是「一个语向一个模型」，默认包只有 zh/en/ja， 凑不齐五语 —— 所以 languages 允许是五语的非空子集。 但越界（fr/de/ru）一样拒绝，子集不是放水。

kindenginelanguages必需文件
asrsherpa-sensevoice恰好五语model.int8.onnx · tokens.txt · silero_vad.onnx
translationllama-qwen2 / llama-gemma3恰好五语model.gguf
opusopus-mt-marian五语非空子集routes.txt · norm/nfkc.bin

契约三处同步：scripts/model_pack.py · ios/…/ModelPackages.swift · app/…/ModelPackages.java。回归测试从 17 项加到 20 项。

opus 是「非必需」的（Kind.isRequired == false）： 没有它不该拦住用户开始录音。Android start() 里也刻意不校验 opus —— 传 null 进 Pipeline，由设置档位判定后回落。

四、两个真 bug（本轮顺手挖出来的）

① bundle-models.py 会静默把内置包降档

脚本原本的默认策略是「每个 kind 取体积最小的包」。而实际内置的 translation 是 Q4_K_M（依据：armv8-a 基线下 Q4_K_M 速度口径第一，质量又优于 Q4_0；Q4_0 还会在中译粤时 稳定复读崩坏）。偏偏 models/ 里 Q3 更小 —— 于是：

任何一次不带 --pick 的重跑（README、build-ios.sh 的提示、 报告里的命令全都不带）都会把两端内置包一起从 Q4_K_M 静默降到 Q3， 而输出是「成功、体积还变小了」—— 看日志完全发现不了。
候选体积旧策略现在
qwen25-1.5b-q3882 MB会被选中跳过
qwen25-1.5b-q4_01017 MB跳过跳过
qwen25-1.5b-q4km1066 MB会被跳过选中（钉住）

修法：脚本顶部加 DEFAULT_PICKS 把三档钉死，表里没有的 kind 才回落取最小； 输出里写明每一档的依据（--pick 指定 / DEFAULT_PICKS 钉住 / 回落取最小）；钉的包不在 models/ 下时写 stderr 说清楚，不假装选中了它。

② 用户导入后来源永远显示「内置」

ModelPackages.install() 的 ZipFile 快路径漏了 remove(kind+"Bundled") （流式路径 unpack() 一直有）。后果：先内置、之后又导入自己包的用户， 设置页会一直标「内置」，而且不显示「恢复内置」入口 —— 三档之后更容易撞上。

写了两支自建检查器，都做了反例测试（注入故障确认它真的会失败）： 

# Java：tree-sitter 的 Java 语法做真解析，报 ERROR / MISSING 节点
$ python3 scripts/check-java-syntax.py
✓ 8 个 Java 文件的语法都通过

# native：clang++ -fsyntax-only + 运行时生成的最小 jni.h 替身（不入库）
$ python3 scripts/check-native-syntax.py
✓ app/src/main/cpp/vt_opus_jni.cpp
✓ native/nmt/vt_opus.cc
✓ …/ssentencepiece/csrc/ssentencepiece.cc
写第一版 Java 检查器时踩了一格，值得记下来： tree-sitter 的 MISSING 节点 type 是「缺的那个 token 本身」 （少一个分号时 type == ";"），不是字面量 "MISSING"。 我按 node.type in {"ERROR","MISSING"} 写，结果一条都报不出来， 输出照旧是「✓ 全部通过」。靠反例测试才抓到。 任何自建检查器，都必须先用故意写坏的输入验一遍「它真的会失败」。

七、仍未打勾的一格：A8 真机实跑

iPad mini 4 就连在 USB 上（ios-deploy -c 能看到 J96AP / 15.8.8）， 真机构建也过了 —— 但安装这一步被设备的锁屏挡住了： 

[  0%] … iPad mini 4 … connected through USB, beginning install
Error 0xe800001a: The device is passcode protected.
     AMDeviceSecureTransferPath(0, device, url, options, transfer_callback, 0)

解锁后重跑即可（脚本里已有这条排障说明）： 

bash scripts/install-ipad.sh --udid c025104116a3f342e1cabcfecfff2ed459d7d05d
所以「A8 上的绝对速度」依旧没被观测过。 已确认的只是：代码在 arm64 真机目标上编得过、端侧 C++ 与 Python 参考实现 20/20 逐字一致、 导入/装载/路由的逻辑都有回归保护。真正没验的是这一颗 CPU 上装载要多久、第一句要多久 —— 仍然是整个项目最大的未知数。
