一、上游核查：为什么没有「直译」这条路

逐个核过 Helsinki-NLP 在 HuggingFace 上的完整清单（hf-mirror API，按模型 id 精确检索）：官方 opus-mt-ja-* 系列里没有任何以 zh 为目标的模型。

检索结果说明
opus-mt-ja-ar / -bg / -da / -de / -en / -es / -fi / -fr / …有 21 个日→英、日→德、日→法… 唯独没有 ja→zh
opus-mt-ja-zh / opus-mt-tc-big-ja-zh不存在HF 上无此模型
opus-mt-tc-big-zh-ja存在只有中→日单向，且已是现役 zh-ja 用的包
结论：ja→zh 只能走 ja-en → en-zh 两跳（日→英→中），两跳解码、误差累积。 这也是它成为四向里最弱一向的根因，不是包的问题。

另：社区有反向模型（shun89/opus-mt-ja-zh 等，Apache-2.0），但无现成 ONNX、质量未验、非官方出品，上架需自担风险 —— 本轮未采用，与 2026-09-28 门禁的处置一致。

必须说清楚的两点：
  1. ja-zh 的 4 条用例里有 3 条判负，其中部分是 critical_terms 字面匹配过严（如「明早」vs「明天」、「電車→火车」）。 即便如此，75% vs 50% 的方向是确定的 —— 它在四向里唯一明显落后。
  2. 20 条语料的判定粒度是 5%，不足以支撑「质量接近」的结论。本轮启用不是因为质量够了，而是因为延迟差 20 倍。

五、注意事项与遗留

  • 包体积 +139 MiB。两端内置合计由 777 MiB 增至 912 MiB（iOS 侧已实测为 du -sh ios/BundledModels = 912M）；Android APK 会相应变大。
  • 已导入过旧版 opus 包的设备要重新导入。取包入口是 selected = installed ?? bundled —— 用户手工导入的旧包（routes.txt 里没有 ja-zh）会遮蔽新的内置包，表现为「日译中还是走通用模型」。在设置页重新导入或先「移除」即可。
  • 版本号与更新日志未动。iOS Info.plist / Android build.gradle 的版本号、两端「更新日志」条目均未改（这属于发布动作）。gen-ios-project.py 也未重跑 —— BundledModels/ 的目录结构没变（仍是 asr/ + opus/ 两个 folder reference），工程引用无需更新。
  • APK 未重打。dist/android/ 下仍是旧版（不含 ja-zh 接线）。
  • 真机未验。上述全部是构建期验证 + 端侧 C++ 对撞；iPad mini 4 上的日译中端到端仍待实测。
  • 质量仍是四向里最弱。「日译中走 OPUS」的收益是速度，不是准确度；对质量敏感的场景可切「统一模型」档。
