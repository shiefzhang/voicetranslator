一、先定位：为什么确信不是「按钮坏了」

用一个很省事的判别法：在同一页面里找已知能用的同类控件，比对它们用的 API。 设置页里「查看版本更新记录」走 sheet、翻译页的菜单走 Menu， 都没有被报故障；三个坏掉的项则共用 confirmationDialog。 API 分布和故障分布完全重合，嫌疑就锁定了。

主语言 · confirmationDialog
翻译语言 · confirmationDialog
分享内容 · confirmationDialog
版本记录 · sheet
翻译页菜单 · Menu

再往下看 SettingsView 的修饰符挂载点，问题就完全摊开了 —— 四项全都挂在哪同一个根视图上。 

// 修改前：SettingsView 最外层 VStack 上叠了 4 个 presentation 修饰符
VStack(alignment: .leading, spacing: 0) { /* 页面内容 */ }

    .sheet(isPresented: ...) { changelogSheet }
    .fileImporter(isPresented: ..., ...)

为什么这个 bug 特别难查：两条机制都静默失败 —— 不崩溃、不打印日志、 不留痕迹。代码能编译、能运行、按钮状态也确实变了，只是界面上什么都不发生。 所以「构建通过」在这里完全不构成任何证据。

三、修法：每个视图层级只留一个 presentation 修饰符

入口 承载方式 挂在哪
主语言 / 翻译语言 / 分享内容 一个 .sheet(item:)
+ 统一 PickerTarget 枚举 		body 根的 VStack —— 全页唯一槽位
版本更新记录 .sheet(isPresented:) aboutSection 自己身上 —— 独立槽位
转写 / 翻译模型包 .fileImporter
binding 里用 kind 过滤 		各自的 modelRow —— 独立槽位

两行共用一份 @State，所以要过滤，否则两个 fileImporter 会同时激活： 

private func importerBinding(for kind: ModelPackages.Kind) -> Binding<Bool> {
    Binding(
        get: { showImporter && importingKind == kind },
        set: { if !$0 { showImporter = false; importingKind = nil } }
    )
}

顺带把「选一项」统一成 sheet(item:) + 一个枚举，而不是 N 个独立弹窗。 好处不只是绕开冲突：「当前在显示哪个弹窗」被收敛成一个状态， 上面那条规则才有可能被真正遵守，而不是靠自觉。

五、状态层的净减少

Android 那套「行点击 → 写入待选目标 → 弹窗绑定该目标非空 → 关闭时清空」的写法， 在 iOS 上是三处状态必须互相一致，而只要弹窗因为上面任一原因没弹出来， 这个标记就会一直被留在那儿。 改为让选择器自己持有该状态：

改动结果
删除 @Published var editingLanguage 少一个需要在 View 与 Model 之间同步的状态
requestLanguageChange(_:) → canChangeLanguage() -> Bool 变成纯判断，不再往 Model 里写「待选目标」
commitLanguageChange(to:) → commitLanguageChange(to:target:) 目标显式传入，不依赖隐式状态
performChange(target:code:key:) 去掉 key 这个参数本来就没人用，是历史死参数

七、仍未验证的部分

这次修的是「点了有没有反应」，不是「翻译能不能用」。 两者是不同层级的问题，不要混为一谈。
  • 真机端到端仍未实测：录音 → VAD → SenseVoice ASR → llama 翻译。 模型包已在设备上，但需要在 iPad 上人工导入并跑一遍。 A8 芯片跑 1.5B Q3 翻译模型的延迟、发热、内存占用都还没有实测数据。
  • 粤语译文质量未验证：1.5B Q3 能否稳定输出地道粤语，属于模型能力问题， 与本次呈现层修复无关。
  • 模拟器验证不到这类问题：iPad 上的 popover 锚点问题在模拟器上 会以居中模态呈现，根本复现不出来。这类修复必须装到真机上看。
