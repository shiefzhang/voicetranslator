一、结论

  1. Q4_0 确实是速度最快的量化格式，而且是断层第一。同模型同条件实测，prefill 比现役 Q3_K_M 快 3.3 倍、生成快 30%。更小的 Q3_K_S / Q5_0 反而更慢 —— 量化档位和速度不是单调关系。
  2. 但 Q4_0 不能做默认翻译包 —— 它的粤语会稳定复读崩坏。2026-09-24 的回归实测里，中译粤从「嘅食嚟」一路复读「嚟」到 256 token 上限，两次独立运行结果一致；中译韩混入 free / invitation 英文实词。而现有 script_ok 只校验「无假名 / 无韩文 / 含 CJK」，整串复读垃圾照样通过校验。另外对 A8~A12 的设备，Q4_0 的加速根本拿不到（repack 需 DOTPROD）。结论：Q4_0 可以留作可选包，但不该做默认。详见第六节。
  3. 去掉粤语也救不了 Q4_0 —— 它的中译韩会混入英文实词。官方 Q4_0 与「从 F16 重新量化的 Q4_0」在同一句上逐字相同（free / invitation），说明这是 Q4_0 格式在 4.77 bpw 下的固有限制，换来源救不了。要速度首选 Q4_0；要「速度 + 缺陷最轻」选 IQ4_NL。详见第七节。
    但这两条都有前提 —— 设备必须支持 dotprod。目标机 iPad mini 4 没有，第八节会给出不一样的答案。
  4. Qwen3.5 同规模不会更快，慢一倍多。同为 Q4_0 格式，Qwen3.5-2B 的生成只有 Qwen2.5-1.5B 的 39%（参数只多 5.6%）。它的质量其实不输（中译粤甚至更好），所以这是「拿一倍的延迟换一个不必要的质量提升」，方向反了。
  5. Qwen3.8 与端侧无关。它是 2.4T 参数旗舰，只开源 27B，没有 1.5B 级小尺寸。
  6. 「更小的模型」确实更快，但 Qwen3.5-0.8B 质量不可靠。它绝对速度第一（prefill 5.0x / 生成 1.8x），但英译中单句就凭空多出「十点半前」这类原文没有的内容，不建议上生产。
  7. 目标机 iPad mini 4（A8）的答案不一样：Qwen2.5-1.5B + Q4_K_M。在 armv8-a 基线口径（2 线程）下，四档 1.5B 挤在 1.2 倍以内，而且最慢变成最快反过来 —— Q4_K_M 第一（比 Q4_0 快 8% / 5%），因为 Q4_0 的加速依赖 A8 根本没有的 dotprod。换 0.5B 虽然快 2.7 倍，但 5 个用例只对 1 个、且都是语义级错误。详见第八节。
    已按此把两端内置翻译包换成 Q4_K_M（2026-09-24），并构建验证通过。
  8. 「换新一代」不等于更快：Qwen3-1.7B 更慢、也更差。它比现役只多 12% 参数、体积几乎持平，但在目标机口径下慢 8~11%，5 个用例比现役多错一格（中→日把「洗手间」写成中文汉字「洗手間」），中→韩错得更重（Q4_0 甚至整句输出中文）。1.5B 换 1.7B 是负收益，详见第九节。

为什么 Q4_1 比 Q4_0 慢 3.6 倍

看着反直觉，但根因清楚：ARM 上只有 Q4_0 / Q8_0 有 repack 快速路径。ARM 侧的 repack 实现整体被这个条件包住（ggml/src/ggml-cpu/arch/arm/repack.cpp:26）：

#if defined(__aarch64__) && defined(__ARM_NEON) && (defined(__ARM_FEATURE_MATMUL_INT8) || defined(__ARM_FEATURE_DOTPROD))

Q4_1 / Q5_0 不在这条路径里，只能走通用 C 路径，于是「更小的量化」没有换来计算优势。K-quant 有自己的一套 repack（decode_q_Kx8_6bit_scales），这解释了 Q4_K_M 的 prefill（114）为何远高于 Q3_K_M（50）—— 但仍然追不上 Q4_0。

顺带确认：GGML_CPU_REPACK 默认是 ON（ggml/CMakeLists.txt:152），且 baseline 构建下它被整体编掉（因为没有 DOTPROD）。这解释了「baseline 下 Q4_0 与 Q3_K_M 打平、开了 dotprod 才拉开差距」—— Q4_0 的加速和 dotprod 是绑定的，两项必须一起做。

IQ4_NL 是值得注意的第二名

体积与 Q4_0 完全相同（1017 vs 1011 MiB），速度 0.81x / 0.94x，而 4.5 bpw 的非线性量化质量通常明显优于 Q4_0。要速度与质量兼顾，IQ4_NL 比 Q4_0 更稳。

三、Qwen3.5 会更快吗 —— 实测答案是不会

3.1 架构差异

Qwen3.5 的小尺寸实际只有 0.8B / 2B / 4B / 9B（没有 1.5B）。以 2B 为例，config.json 显示：

  • 混合注意力：24 层里 18 层是 Gated DeltaNet 线性注意力，只有 6 层是全注意力（full_attention_interval: 4）
  • 词表 248320（现役 Qwen2.5 是 151936，+63%），且 tie_word_embeddings: true
  • GGUF 的 general.architecture = qwen35，本仓库的 llama.cpp 已支持（LLM_ARCH_QWEN35）
  • 天生多模态，但视觉塔在独立的 mmproj-*.gguf 里，文本权重不含视觉张量

3.2 速度：同 Q4_0 格式的公平对照

生产真实 prompt（约 165 token 输入 / 18 token 输出），4 线程，全部走下面第四节说的干净通道。

模型prefill t/s生成 t/spp160 (t4)tg20 (t1 / t2 / t4)
Qwen2.5-1.5B Q4_0150.834.9165.5828.39 / 37.75 / 40.44
Qwen3.5-2B Q4_094.613.7123.8317.17 / 21.37 / 23.41
比值0.63x0.39x0.75x0.60x / 0.57x / 0.58x

参数只多 5.6%（1.88B vs 1.78B），生成却慢到 39%。线程伸缩比两者接近（1.42x vs 1.36x），说明不是并行度问题，是 GDN 层本身在 CPU 上的单步效率就低。GDN 的长处是长序列下 KV cache 恒定，而本项目场景是「165 token 输入 / 18 token 输出」—— 这项优势完全用不上。

方法学修正（重要）：本轮一度依据 tg128 得出「Qwen3.5 加线程无收益」，被 tg20 三次重复推翻（21.37 → 23.41，正常增长）。短序列 bench 方差大，下结论前要看 t=1 基准 + 多次重复。

所以问题不在质量，在速度。Qwen3.5-2B 的中译粤反而明显最好 —— 它保住了「食咗」，而现役模型输出「明嘅我喺香港嘅嘢去出差」整句崩坏。中译日两者都正确。用它是在拿一倍的延迟，换一个「可用但不必要」的质量提升。

⚠️ 一条必须撤回的中间结论。本报告早期版本曾记录「Qwen3.5-2B 中译日幻觉出 おしんちん」。复现后确认那是测量方法的问题，不是模型的问题：gguf 自带 chat template 时，llama.cpp 默认 auto-enable 会话模式，喂进去的完整 prompt 会被当成 user message 再套一次模板，输入结构被污染。加上 -no-cnv 走干净通道后该幻觉消失，所有模型的中译日都正确。遇到「目标语言里混进源语言字符」或「莫名多出思考过程」，应先怀疑 prompt 通道，再怪模型。

三点必须一起看：
  1. 复读是可复现的，不是偶发。同一用例独立跑两次，都从「嘅食嚟」开始一路复读「嚟」到 256 token 上限。生产里也是 greedy 采样，等于每次都会踩。
  2. 现有校验拦不住。复读出来的全是汉字，script_ok("Cantonese") 只校验「无假名 / 无韩文 / 含 CJK」，整串垃圾照样通过，用户会等十几秒然后拿到一屏「嚟嚟嚟」。
  3. 对 iPad mini 4 而言这次换包是纯亏。Q4_0 的加速来自 ARM 的 repack 快速路径，而那条路径被 __ARM_FEATURE_DOTPROD 整体包住 —— A8 没有 DOTPROD，baseline 下 Q4_0 与 Q3_K_M 速度打平（第二轮已实测）。于是换到目标机上只剩两个后果：质量变差、包大 135 MiB。

客观地说，三档的粤语都不合格（Q3_K_M「明嘅」、Q4_K_M「明月」也都是错译）。但「复读填满输出」和「译错一个词」是两个量级：前者会让一次翻译彻底不可用，而且长度是后者的十几倍、更慢。粤语这一路真正需要的是 prompt 侧的输出校验（n-gram 重复检测 / 目标语言字符集校验），不是换量化。

七、去掉粤语之后 —— IQ4_NL 与「从 F16 重新量化的 Q4_0」

第六节的结论是「Q4_0 不能做默认」，但粤语占了理由的一大半。那么把粤语从评估里整个去掉，Q4_0 是不是就能用了？这一节专门回答这个问题，同时把 IQ4_NL 拉进来同场对比。

方法学修正（这次做对的地方）：报告第二节那个速度矩阵里的 IQ4_NL 是从 Q4_K_M 二次量化出来的，只适合比速度，不能用来判断质量（bench-llama-arm.py 的 docstring 里已经记了这个教训：二次量化的 Q4_0 曾把「to Shanghai」译成「从 Shanghai」）。
这次发现官方 GGUF 仓库里有 qwen2.5-1.5b-instruct-fp16.gguf，于是下 F16 原始权重重新量化（llama-quantize，不带 --allow-requantize），IQ4_NL 和对照用的 Q4_0 都是这么来的。

来源中→韩译文

八、iPad mini 4 该用哪个模型 —— 按目标机口径重测

决策点结论依据

如果 iPad mini 4 必须做到「能用」，方向不是换量化档位，而是换引擎 —— 上 400M 级的专用 NMT（端侧翻译引擎评估.html 已评估 M2M100-418M 这条路）。参数量小一个数量级，速度收益远大于任何量化技巧，代价是模型与运行时都要重做。

九、Qwen3-1.7B 值得换吗 —— 更慢，而且更差

第三节评估的是 Qwen3.5，这一节是它的前代 Qwen3（别混淆）。Qwen3-1.7B 参数量 1.72B，只比现役的 1.54B 多 12%，架构也几乎一致（28 层、16 头 / 8 KV 头的 GQA），是「同规模换一代」的最直接候选。模型取 unsloth 的官方量化（Qwen3-1.7B-Q4_K_M / -Q4_0，从 BF16 正规量化，不是二次加工）。

先说一个方法论前提，避免重复上次的坑。Qwen3 是有 thinking 能力的模型，prompt 里必须在 assistant 后补一个空 think 块才能让它直接输出译文。这次的空块写法是从官方 tokenizer_config.json 的 chat template 里逐字抄的：
{{- '<think>\n\n</think>\n\n' }}
而不是凭印象写的 —— 所以下面的结论不是「模板没配对导致的假失败」（那个教训见第三节）。

两条要注意的：

① Q4_0 对 Qwen3 的破坏比它对 Qwen2.5 的破坏更重。同一份 prompt 下，Qwen3 Q4_0 出现了整句输出中文（中→韩）和把「すみません」译成「谢谢」（日→中）这类实义错误，而 Qwen3 Q4_K_M 在这两句上是「错得轻一些」的（虽然中→日仍有问题）。这再一次说明 Q4_0 不该做默认。

十、复现方法

  • python3 scripts/bench-llama-arm.py —— 从 .vtmodel 解出 gguf，按 --archs / --threads / --quantize 跑速度矩阵，输出相对加速比
  • python3 scripts/check-translation-quality.py <model> --case en2zh,zh2yue —— 用生产 prompt 跑固定例句，并排打印译文 和 该 prompt 下的真实 prefill / 生成速度。--arch armv8-a 切到目标机的基线指令集（只影响速度、不影响译文），--shots 1..3 试 few-shot 组数

第八节（目标机口径）的做法 —— 关键是单独编一套基线指令集的二进制，不是在同一份构建上改线程数：

# 1) 编两套，各自独立构建目录
for ARCH in armv8-a armv8.2-a+dotprod+fp16; do
  tag=$(echo $ARCH | tr '+' '_')
  B=.tools/quality-check/build-completion-$tag
  cmake -S ios/third_party/src/llama.cpp -B $B -DCMAKE_BUILD_TYPE=Release \
    -DGGML_NATIVE=OFF -DGGML_CPU_ARM_ARCH=$ARCH \

踩过的坑（下次直接绕开）

  • -no-cnv 是评测的生死线。gguf 自带 chat template 时 llama.cpp 默认 auto-enable 会话模式（日志：chat template is available, enabling conversation mode），喂进去的完整 prompt 会被当成 user message 再套一次模板。本报告早期的一批质量数据就是这么被污染的。
  • 工具别选错：llama-cli 是会话工具且不接受 -no-cnv（报了也照样进交互模式）；llama-completion 是补全工具，接受 -no-cnv。正确组合只有 llama-completion -no-cnv。
  • 输出流：-no-cnv 下 stdout 里只有译文、stderr 全是日志；会话模式下 stdout 可能全空。提取译文时不要把译文行丢进整行黑名单 —— 「[end of text]」这种尾巴会让整条译文被误杀。
  • Qwen3 / Qwen3.5 的「no-think」写法必须从 gguf 里读，别凭印象。这两个架构要在 assistant 后补一个空 think 块（否则模型会开始长篇思考）。Qwen3-1.7B 的 gguf 自带模板里，enable_thinking is false 分支逐字是 '<think>\n\n</think>\n\n' —— 用它之前先 python3 scripts/gguf-kv.py <m.gguf> tokenizer.chat_template --full 核对一眼，几秒钟的事，写错就是整轮数据报废。
    本项目硬编码拼 prompt、不走 Jinja，所以必须自己补；而且要先按 gguf 的 general.architecture 判断补不补 —— Qwen2 / Qwen2.5 没有 thinking 概念，补了会被当成正文输出。分隔符 <|im_start|> / <|im_end|> 各代一致。
  • GGUF 的 KV 类型枚举别凭记忆写。STRING=8 / ARRAY=9（不是 0/1 —— 按定义顺序排是 UINT8..BOOL 占 0~7）。类型错一个，后面偏移全部错位，症状是读元数据时抛 MemoryError（把随机字节当字符串长度）。读元数据直接用 scripts/gguf-kv.py（本轮新增，读任意 gguf 的 KV 元数据），不要每次现写 inline 解析。
  • 用 subprocess 调用 llama 系工具必须传 stdin=subprocess.DEVNULL，否则进程生成完后等 stdin，脚本会挂死。
  • 下模型走 ModelScope，别走 hf-mirror。同一天实测：hf-mirror 0.18 MB/s（3.5 GB 要下 4 小时），ModelScope 3.9 MB/s —— 快 22 倍，而且 ModelScope 的 CDN 带 accept-ranges: bytes，可以分段并行。hf-mirror 还不支持 -C - 断点续传（重试从头覆盖）。
  • ModelScope 分段下载的坑：它的 API 会 302 到 CDN，而 CDN 的 206 响应不带 Content-Range，所以「先 -r 0-0 读总大小」这招失效（只会拿到 content-length: 1）。总大小要从不带 Range 的响应头里取 content-length，且必须取最后一个 —— 前面那个 369 是 302 响应体的大小。
  • 换量化档位必须从 F16 重新量化，不能用 --allow-requantize 二次加工。二次量化的 Q4_0 曾把「to Shanghai」译成「从 Shanghai」；本次的 IQ4_NL 也是从 F16 量的，才有资格拿来判断质量。
