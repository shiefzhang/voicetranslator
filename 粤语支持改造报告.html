包的 name 写着「中日韩英粤」，而项目里有 五处一致要求「恰好中日韩英四语」。 只要有一处不满足，包就被整体拒绝 —— 不是降级，是装不进去。

关键事实：App 里根本没有粤语。 Language.swift 的 VT.codes 只有 zh/ja/ko/en/fr/de/ru —— 所以包声明 yue 没有任何正面作用，唯一效果就是把整包拖死。 这也说明这批包是**有意**走在前面、App 侧尚未跟上。

2 · 决策：正式支持粤语

在「改包」「放宽契约」「正式支持粤语」三条路里选了第三条 —— 语种契约升级为 恰好五语，粤语既是主语言（ASR 输入）也是翻译目标。

项值说明
VT.codes zh ja ko en yue fr de ru yue 插在索引 4，三个数组必须索引对齐
speechCodeCount 4 → 5 主语言候选 = 前 5 个；法/德/俄仍只能作目标语言
ASR sense_voice.language = "yue" SenseVoice 上游导出本身就带 lang_yue，零改动
翻译 engineName → Cantonese prompt 走粤语分支
反向页 目标在前 5 个即可用 reverseAvailable 加了 yue

3 · 最容易炸的一处：语种脚本校验

// 兜底分支的语义其实是「不含任何汉字」
if(target=="Chinese")return !kana&&!hangul&&cjk;
if(target=="Japanese")return kana&&!hangul;
if(target=="Korean")return hangul&&!kana;
return !kana&&!hangul&&!cjk;        ← 粤语译文全是汉字，必然落进这里
不显式加分支，粤语翻译会走成这样： 判为错误语种 → 用重试提示词再生成一次 → 仍然判错 → 直接抛 「模型两次返回错误语种，请缩短句子或更换翻译模型包」。 也就是说翻译功能会 100% 失败，而且失败原因看起来像模型问题，不像代码问题。

修法：粤语与中文合并为同一分支 —— case "Chinese", "Cantonese": return !kana && !hangul && cjk。 Android 的 C++ 侧写法对应（||），两端语义一致。

已知局限（已写进代码注释与 README）：粤语与普通话同为 CJK 汉字， 码位无法区分，所以「模型把粤语写成普通话书面语」这种情况查不出来 —— 只能靠 prompt 里的 rule("Cantonese") 约束。 日/韩能用假名、Hangul 做兜底，粤语做不到。这是设计上的天花板，不是本次引入的缺陷。

4 · 粤语的 prompt 素材

iOS 的 PromptBuilder.swift 与 Android 的 translator.cpp 必须逐字一致， 否则同一句话在两端会译出不同结果，回归比对直接失败。以下五段两边完全相同。

片段值
native粤语
hello你好。（与中文相同，有意为之）
book呢本系一本书。
hospital最近嘅医院喺边度？
rule只使用粤语白话字（如「嘅」「喺」「唔」「咗」），不要写成普通话书面语，禁止日语假名和韩文。

hello 与中文相同是刻意的：few-shot 靠 book / hospital 体现粤语特征就够了，不必为了区分而硬造不自然的问候语。

7 · 现在可以导入了

两个模型包已在 iPad mini 4 的 App Documents 里（覆盖安装保留了数据）， 新 App 也接受它们的语言声明了。剩下的步骤在设备上：
  1. iPad 上打开 App → 设置 → 「转写模型包」→ 选择模型包
  2. 文件选择器里进 我的 iPad → 多国语音互译（因为 UIFileSharingEnabled=true）
  3. 选 sensevoice-zh-ja-ko-en.vtmodel，等校验通过
  4. 同法导入 qwen25-1.5b-q3-zh-ja-ko-en-yue.vtmodel（882 MB）
  5. 设置里把主语言切成 粤语，试说一句粤语看转写与译文
导入时的空间占用要留意。App 会先把文件复制到 Caches 再解包到 Application Support， 所以峰值约为源文件的 3 倍：导入 882 MB 的翻译包时，加上已装的 229 MB ASR 包， 峰值需要约 2.9 GB 空闲。iPad mini 4 若是 16/32 GB 版本会比较紧。 导入完成后可以在「文件」App 里删掉 Documents 里的源文件释放空间（已激活的模型不受影响）。
