这一轮拿到了决定性证据 —— 从 iPad 里拉出了两份真实崩溃报告，它们指向同一条语句： 录制切帧时的 removeFirst 越界。这不是推测，是设备自己写下来的现场。

一页结论

闪退原因：AudioCapture.process(_:) 里的一次数组越界断言。

录制把采样切成一帧一帧往外回调；而回调的接收方在「朗读暂停」分支里会同步停掉录音、 把缓冲清空。回调回来时，切帧循环手里那个下标已经指向空缓冲， 循环退出后的 removeFirst(下标) 直接触发 Swift 运行时断言 → SIGTRAP。

朗读一旦发生，这条路径必走一遍 ⇒ 必崩。所以症状精确表现为「朗读完第一句就没了」。

二、为什么会越界：一条必走的链

改动前的切帧是这样的（AudioCapture.swift）：

var offset = 0
while pending.count - offset >= Self.frameLength {
    let frame = ContiguousArray(pending[offset..<(offset + Self.frameLength)])
    offset += Self.frameLength
    onFrame?(frame)          // ← 在循环里回调出去
}
if offset > 0 { pending.removeFirst(offset) }   // ← 崩溃点

而 onFrame 的接收方在「朗读暂停」分支里做的是（Pipeline.swift）：

if stateLock.withLock({ playbackHold }) {
    self.audio.stop()        // ← 已在采集队列 ⇒ 立即执行
    ...
    Thread.sleep(...)        // 阻塞等朗读结束
    self.resumeCapture(...)  // → audio.start()，又一次清缓冲
}

把两头接起来，崩溃就是这么发生的：

#发生了什么缓冲状态
1process 开始切帧，offset 累加到 512pending 有数据
2回调 onFrame(frame) 进入 Pipeline 的朗读暂停分支—
3audio.stop() —— 因为在同一条队列上，立即执行被清空
4阻塞等朗读读完，再 audio.start()（内部又一次清空）还是空
5回到循环：0 - 512 < 512 → 退出空
6pending.removeFirst(512) —— 空数组上取 512 个💥 SIGTRAP
关键在于 stop() / start() 在采集队列上是「立即执行」。 它们本来是为「别的线程调用」设计的（那时会排到队尾、不会插进 process 中间）， 但从 onFrame 里调进来时，我们是站在同一条队列上的 —— 于是插了个正着。

三、怎么修的

不去改「谁在回调里停了录音」（那是既有架构，改动面太大）， 而是让 process 不再跨过回调持有缓冲下标：

var frames: [ContiguousArray<Float>] = []
var offset = 0
while pending.count - offset >= Self.frameLength {
    frames.append(ContiguousArray(pending[offset..<(offset + Self.frameLength)]))
    offset += Self.frameLength
}
if offset > 0 { pending.removeFirst(offset) }   // 先收缩干净
for frame in frames { onFrame?(frame) }          // 再逐帧回调

回调之前，缓冲已经收拾完毕；回调方再清、再停、再启，都碰不到已经算好的这次切帧。 语义完全不变（每帧仍然回调一次），只是把「结算」提前了。

顺带说明 v0.2.13 那个改动是什么。 上一轮我把 installTap 的显式 format: 改成 nil， 理由是「朗读来回切会话后格式可能不一致 → 抛 ObjC 异常 → SIGABRT」。 那是一个真实存在但这次没发生的隐患（属于防御性加固）， 不是本次闪退的原因。真正的原因要等真机崩溃报告出来才看得见 —— 这也正是上一轮补「落盘日志 + 崩溃捕获」的意义：没有它，这一轮照样只能猜。

五、Android 侧有没有同样的问题

没有。两端采集的形态不同：

端采集形态会有这个问题吗
iOStap 回调 queue.async 派发；切帧缓冲 pending 是成员变量； 回调从切帧循环里发出去会 —— 回调期间缓冲可被外部清空
Android单线程 while(recording) 里 read；缓冲 short[] buffer 与计数 have 都是栈上局部变量；暂停分支末尾是 continue 回循环顶 不会 —— 没有成员缓冲、也没有「拿旧下标回去算」的机会

所以这一版只动 iOS，Android 版本号保持 0.2.12 不变。
