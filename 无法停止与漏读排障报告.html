两件事一件确凿、一件是推断 —— 下面把哪件有证据、哪件只能算推断，分开写清楚。

一页结论

① 停不下来 —— iOS 漏了「采集结束」这一刻，确凿。

主循环等的是一个叫 captureDone 的标志，而它在会话进行中永远是 false： 全仓库只有 finally 里才置真。于是按了停止之后主循环无限空转、收尾回调一辈子不来 —— 界面停在「录音已停止，正在处理剩余句子…」，而且之后再也开不了新会话。

② 第二句没朗读 —— 等待窗口里开出了第二条朗读，推断。

朗读在等录音让出音频会话时，那个「等待」是异步的（最长 0.5 s）。窗口里 speech.isSpeaking 和 speechHoldActive 都还是 false， 于是第二条译文会抢着开始 —— 后一条的 speak() 把前一条当场打断。

窗口只有 50~150 ms，是概率事件，没拿到真机日志坐实。两条修法都落地并加了日志； 若再复现，导出诊断日志即可定案。

一、停不下来：一个永远等不到的信号

流水线的收尾靠这个循环（Pipeline.run()）：

while !(stateLock.withLock { captureDone }) || !asrJobs.isEmpty { … }

而 captureDone 在整个仓库里只被置真一次 —— 在 finally 里。 换句话说：会话跑到一半时它是 false，循环就恒真；而 stop() 只置了 stopRequested（不是 cancelled），所以这个循环退不出去。

对照 Android —— 它是怎么收尾的

Android 的采集是一条真正的线程，循环条件里就带着停止条件，退出即进 finally：

// Pipeline.java：采集线程
while (recording && !stopRequested) { … }
finally { recording=false; segmenter.flush(); latest.set(null);
          captureDone = true; … }
iOS 没有「采集线程的 finally」这个时刻可以挂。它的帧是 installTap 回调派发过来的 —— 没有循环，也就没有循环退出那一刻。这就是漏掉它的原因， 也是为什么必须为它单独加一条回调。

修法：四步，一步都不能挪

private func captureEnded() {
    guard stopRequested || cancelled || !recording else { return }  // ① 只认「真的结束」
    let leftover = segmenter; segmenter = nil                     // ② 先摘引用（防递归）
    leftover?.flush()                                             // ③ 再冲刷残留半句
    stateLock.withLock { captureDone = true }                      // ④ 最后才放行主循环
}
#不能动的地方挪了的后果
①守卫三个记号：stopRequested / cancelled / !recording 朗读暂停、积压暂停也会 audio.stop() —— 少了守卫，朗读一发生就会被当成「会话结束」
②先摘 segmenter 引用 「转写队列满」那条路会在回调里再停一次采集 ⇒ 递归回来 ⇒ 同一段音频被当成两句提交
③flush() 排在置位之前 主循环在「队列已空」上抢先退出 ⇒ 刚冲刷出来的最后半句永远不被转写
④captureDone = true 放最后同上

另外给 AudioCapture.stopOnQueue() 的早退路径也补了通知： engine.start() 失败时 running 一直是 false， 会话同样需要有人来收尾。

二、第二句没朗读：一个 50~150 毫秒的窗口

朗读之前必须先把音频会话从录音手里要过来，然后等它确实停下再出声。 原来那个「本批已经拿到会话」的标志，是放在异步等待的回调里才置的：

waitForCaptureHeld(attempts: needWait ? 25 : 0, waited: needWait) { [weak self] in
    self.speechHoldActive = needWait      // ← 太晚了
    self.beginSpeaking(request)
}

等待最长 0.5 s。这段窗口里，speech.isSpeaking 与 speechHoldActive 都是 false —— 于是排在后面的第二条译文会把这个状态当成「空闲」， 再走一遍 startSpeech：两条朗读同时在飞， 后一条的 speak() 里那段 stopSpeaking(at: .immediate) 把前一条当场打断。

为什么偏偏是「第二句」：冷启动时翻译慢（首个语向要重跑一遍提示词，10~14 秒）， 用户往往连着说好几句；翻译线程随后把第 1 句、第 2 句的译文挨着吐出来， 第 2 句正好落在第 1 句的等待窗口里。 之后节奏稳定下来（会话一直「热」着、新译文都落在「正在朗读」窗口里），就再也不出现了 —— 与「后面就正常了」吻合。

两条修法

改什么为什么
①标志同步置位再等；「忙」的判定改成
speech.isSpeaking || awaitingCaptureHold		 窗口里来的新译文只允许顶掉待播，不许另起一条朗读
②采集线程退出朗读暂停时
只清 playbackHeld，不碰调用方的 playbackHold		 原来两个标志一起清：调用方刚为下一条置上的请求会被抹掉 ⇒ 它永远等不到「已让出」⇒ 超时后在没让出会话的情况下出声（听感：这句没声音）
③等待期间若调用方又置上了，保持停着继续等 不白跑一轮 停→启，也不让调用方看到「已让出」标志抖动
④停止朗读时把已经发出的暂停请求还回去 不还的话没人会放开采集，麦克风要停到 60 秒兜底才恢复
诚实标注：这一条是推断。窗口只有 50~150 毫秒，属于概率事件， 这次没有真机日志坐实。四条修法都已落地、也都加了日志 —— 若再出现，导出诊断日志看 待播被顶掉 / 打断上一条朗读 / 等采集让出会话超时 哪一行，即可定案。
