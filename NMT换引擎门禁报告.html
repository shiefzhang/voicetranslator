专用 NMT 换引擎：M2M 判死，OPUS-MT 通过

把 OPUS-MT 专向 int8（ONNX Runtime）和现役 Qwen2.5-1.5B Q4_K_M（生产 prompt）在同一台机器、同一套 20 条语料、同一个判据下对撞，覆盖 中↔英、中→日、日→中 四个语向。

结论：门禁通过（promote = True） —— P50 52 ms vs 1322 ms，P95 降 93.1%；代价是关键错误率 35% vs 30%（20 条里 7 错 vs 6 错），且包体降到 709 MB。

09-24 那轮的结论「专用 NMT 并不比 LLM 快」已被推翻：那是 M2M-100-418M 独有的问题（12 层 × 48 个 KV 槽），不是 NMT 这一类的问题。详见第六节。

五、本轮挖出并修掉的三个坑

全部由实测逼出来，不在任何文档里。已逐条写进脚本 docstring 与代码注释。

坑 1（最贵）：quantize_dynamic 不遍历 If 子图 —— 量化静默失败

Optimum 导出的 merged decoder 是「一个 If 包住全部节点、权重挂在顶层 initializer」的结构（use_cache_branch 选首步/增量分支）。onnxruntime.quantization.quantize_dynamic 是基础遍历器，只走 graph.node 顶层，不进子图。

量化前 fp32量化后 int8图里 INT8 初始器
encoder_model437.7 MB109.8 MB（3.99×）72 个
decoder_model_merged （漏传开关）670.0 MB670.1 MB（1.00×）0 个（160 个全是 FLOAT）
decoder_model_merged （EnableSubgraph=True）670.0 MB168.5 MB（3.98×）122 个

修法：quantize_dynamic(..., extra_options={"EnableSubgraph": True})。OR 的 ORT 文档把这条写在 extra_options 的说明里（「Default is False. If enabled, subgraph will be quantized. Dynamic mode currently is supported」）。

为什么这坑特别危险：脚本「成功返回」、日志「打印了大小」、模型「还能跑出正确译文」——只是文件一个字节都没缩小。我们一开始看到 670 → 670.1 MB 时以为是「量化对 merged decoder 无效」，差点就此放弃 zh→ja。
现在脚本会自己断言压缩比（min_ratio=1.6，不达标直接抛错）并且递归走子图数 INT8 初始器，两条独立判据，不再依赖肉眼看文件大小。

坑 2：Marian 两族的 id 空间规则相反，选错就整句 ⁇

族vocab.json 是什么条数正确做法
base（zh-en / en-zh / ja-en）source+target 两份 spm 的合并去重表65001（≈2×32000）查 vocab.json 拿 id
tc-big（zh-ja）就是 target.spm 本身32001（100% 与 tgt spm 一致）用各自 spm 的原生 id（源文 piece 有 3/4 不在 vocab.json 里）

自动判据：len(vocab.json) ≥ 1.15 × max(|source.spm|, |target.spm|) → 合并表（vocab 模式）；否则 → 原生 id。对 5 个包全部命中。

症状识别：选错 id 空间的表现是输出整句 <unk>（解码成 ⁇）或胡言乱语，而且与量化档位无关——fp32 与 int8 输出逐字相同。遇到这种先查 id 空间，别怪量化。

坑 3：Xenova/opus-mt-en-jap 的 ONNX 本身是坏的

该包两种 id 模式都输出乱码（Hello. → オレナ を 切り倒 せ よ .）。排查路径：查 config（eos=0 / start=pad=46275，正常）→ 手搓推理打印 logits（<pad> 每步都是精确 0.0）→ 换 start token（<s>→.、<pad>→乱码）→ 下 fp32 ONNX 对照（fp32 输出与 int8 逐字相同 → 排除量化）→ 用 PyTorch MarianMTModel 取真值（直接喂 source.spm 原生 id 可正常译出 → 模型本身没问题）。结论：上游导出问题，非官方 tc 模型。

影响可控：en→ja 不在本轮需求内（ja→zh 的 pivot 走 ja-en + en-zh，两者都正常）。已判定为上游问题，未修。

六、最有价值的意外收获：Xenova 的 base int8 是坏的，白送 7.6~8.4 倍

第一轮门禁跑出来一个不合常理的数：zh-ja（209M 参数）只要 61 ms，而更小的 zh-en（77M）却要 261 ms。用 ORT 自带的算子级 profiler 一查就明白了：

/lm_head/MatMul_quant（int8）—3.72 ms

也就是说：Xenova 的 _int8 导出让 lm_head 走 fp32 MatMul，并且每步都把绑定词嵌入反量化一遍—— 光这两项就吃掉 237 ms 里的 100 ms。我们自己用同一条管线（fp32 导出 → EnableSubgraph 量化）转出来的包，这两处都是 int8 GEMM。

同一批指令统计（3 次预热后取中位数，单线程组测试）。本报告第三节的全部 OPUS 数字，用的都是自转包 —— 换成 Xenova 的原包，P50 会从 52 ms 退回到 240 ms 量级，门禁依然能过，但优势从 25× 掉到 5.7×。

代价：包体 +16%

自转包把绑定词嵌入多存了一份 int8 拷贝给 MatMulInteger（Xenova 复用了同一份但每步反量化）。base 包因此从 112.7 MB 涨到 145.9 MB（+33.2 MB = 65001×512 的 int8 张量）。用 +16% 体积换 7.9 倍速度，这个交易毫无疑问。

这条的普适意义：不要相信社区预量化包的「int8」字样。同一个模型、同一档位，导出实现的质量差可以到 8 倍。判断方法只有一条 —— 跑 profiler 看 MatMul 还是 MatMulInteger，看 DequantizeLinear 有没有出现在每个解码步里。

七、为什么 OPUS 比 M2M 快、而 M2M 不成立（09-24 结论的修正）

两轮实测放在一起，因果就清楚了 —— 「专用 NMT 比 LLM 慢」这个结论属于 M2M-100-418M，不属于 NMT 这一类。

M2M-100-418MOPUS-MT base（77M）影响
decoder 层数126一半
merged decoder past 槽数48（12 层 × 4）24（6 层 × 4）每 token 在 Python↔ORT 之间搬的张量数减半
参数量418M77M5.4×
每句关键错误率70%35%—
P954995 ms102 ms49×

09-24 那轮总结的四条原因（① 每步搬 48 个 KV 槽；② int8 反量化在 ORT CPU EP 上不便宜；③ encoder-decoder 每 token 算两遍注意力；④ LLM 的 few-shot prefill 是批量的）—— 第 ① 条是主因，而现在它被减半了；第 ② 条在自转包里进一步被消掉（lm_head 不再每步反量化）。

但没有任何一条能证明它在 A8 上依然赢。见第 9 节的边界声明 —— 这个 25× 是桌面读数，不是 iPad mini 4 的读数。

pip 走腾讯镜像（mirrors.cloud.tencent.com，0.9 s）—— 清华镜像在本机走代理要 12.7 s，会卡住。
⚠️ optimum 2.3.0 把 ONNX 导出拆到了独立包 optimum-onnx；只装 optimum 会得到一个 __file__=None 的空壳，报 No module named 'optimum.exporters.onnx'。

九、建议

  1. 「为合规换引擎」这个前提取消。现役 Qwen2.5-1.5B 是 Apache-2.0，现在就能上架；OPUS-MT 各包也全部可商用。许可从来不是障碍。
  2. 「专用 NMT 不比 LLM 快」这个结论撤销。那是 M2M-418M 特有的（48 个 KV 槽 + 12 层）。OPUS-MT 在桌面口径上 P50 快 25×、P95 降 93%，门禁 promote = True。
  3. 但先不要动产品架构。缺一个决定性实验：A8 上的绝对延迟。第 9 节边界里写着——这个 25× 是桌面读数，ORT 的 macOS wheel 降不到 armv8-a 基线，而 llama.cpp 侧能。也就是说：OPUS 的真实优势有多少来自 dotprod，我们完全不知道，而这恰好决定 iPad mini 4 上成不成立。
    建议顺序：① 用 llama.cpp + ORT 在真机（或 A8 级设备）各跑一次同样 20 条；② 再决定要不要引入 ORT 这个新原生依赖。
  4. 架构成本要说清：这不是「换个模型」，是「换一套模型体系」。现在是「单模型包 + 五语契约」（ModelPackages / model_pack.py / verify_model_languages.py 等五处同步）；换 OPUS 等于把它重写成「模型矩阵」——语向数 × 每向一个包，运维量线性增长，且 ja→zh 这种缺口要靠路由做两跳拼接。这在工程上比换引擎本身贵得多。
  5. 落地顺序：先做 zh↔en 两向，别一次铺 4 向。zh↔en 是 291.8 MB、质量与 Qwen 打平（zh-en chrF 0.7577 vs 0.7498，OPUS 反而略优），是最快的回本路径；zh→ja 的 tc-big 要 278.3 MB（单包就占总量 39%）；ja→zh 只能 pivot，是质量最弱的一向（chrF 0.2514）。顺序反了会白花一半工时。
  6. 若「更快」是硬指标，先试这条（比换引擎便宜得多）：Qwen 的 1322 ms 里绝大部分是 3 组 few-shot 的 300 token prefill，而 OPUS 根本没有 prompt。连续翻译时这段前缀逐字相同，可复用它的 KV、省掉每句重复 prefill —— 脚手架已就位（QwenServerEngine.cache_prompt），但至今未跑出数据。粗算 Qwen 可降到 400~500 ms 量级，那时 OPUS 的优势会从 25× 缩到 ~10×，但依然领先。
  7. 语料必须先扩。evaluation/README.md 明确写着内置语料「不能用于模型选型」。20 条的判定粒度是 5%，「35% vs 30%」= 7 错 vs 6 错，一个用例之差。要拍板换不换，得按 README 补到每向 200 条。
本轮实质产出：把「换专用 NMT」从 「已验证，418M 档不成立」推进到 「OPUS 档门禁通过，但优势是否随指令集消失仍未测」；顺手挖出并修掉了 一个会静默失败的量化陷阱与两个 id 空间规则相反的分词陷阱；并且发现社区预量化包比自转包慢 7.6~8.4 倍 —— 这条对任何用 ORT 跑 encoder-decoder 的项目都适用。
评估边界（务必连同结论一起读）： ① 语料仅 20 条，evaluation/README.md 已声明不足以选型，本报告只用于判定方向；判定粒度 5%。 ② 桌面读数，不是真机读数。ORT 的 macOS wheel 由 Apple Silicon 的 dotprod/i8mm 路径编译，无法降级到 armv8-a 基线；Qwen 侧用 armv8.2-a+dotprod+fp16 构建。所以两侧的指令集口径不一致，绝对 ms 不能外推到 iPad mini 4，只有同机相对倍率可用。 ③ 两侧都未在 iOS/Android 真机上测过；ORT 尚未作为原生依赖接入本项目，本报告的 OPUS 全部跑在 macOS Python 进程里（含 Python↔ORT 桥接开销）。 ④ Qwen 侧走 llama-server HTTP（含 ~数 ms 网络开销），且 未开 prompt KV 复用（cache_prompt=False），所以它的 1322 ms 里包含每句重复 prefill 的 300 token —— 这是对 OPUS 有利的口径，第 9 节第 6 条已点明。 ⑤ critical_terms 是字面匹配代理指标：20 条里至少 3 条 OPUS 的 ✗ 属词形/同义未命中而非语义错误（已在第 4 节逐条标注）。两侧都有实义级错误。 ⑥ OPUS-MT 的质量数字是本机实测（20 条）；第七节引用的第三方 FLORES-101 数字（BLEU 22.99 / chrF2 53.98 / 3.73 s）不是本机跑的，仅作旁证。 ⑦ 体积为 encoder_model_int8.onnx + decoder_model_merged_int8.onnx 的本机实测字节数；不含 ORT runtime 本体（libonnxruntime iOS 静态库约 +10~20 MB）与词表/配置。 ⑧ 时间线：第一～五节与第七节的 M2M 数据实测于 2026-09-24；第二、三、四、六节与第八节于 2026-09-28 重测并改写。
